# WWHN-219 — Evidence Chain

This directory documents how WWHN-219 acceptance evidence is produced. The evidence
itself is **not committed**: it is generated by the CI gate on a single exact SHA and
uploaded as an immutable artifact.

## The rule that closes the 70/100 finding

The 70/100 assessment was correct: code, CI, tests, the permission catalog and human
sign-off were not anchored to one immutable chain. Everything below exists to force
them onto one.

**One branch, one SHA, one run, one manifest.**

| Constraint | Enforcement |
|---|---|
| Canonical source only | `.github/workflows/wwhn-219-final-gate.yml` refuses to produce evidence off `m1` |
| One pinned commit | `EXACT_GIT_SHA` written at checkout; manifest rejects a non-40-char SHA |
| Executed, not asserted | Full suite + runtime concurrency both run before the manifest is built |
| Live catalog | Permission catalog is queried from the database after `migrate:fresh --seed` |
| Tamper-evident | `SHA256SUMS` covers every artifact in the directory |

If any commit lands after evidence is collected, the manifest is void. Re-run the gate
and re-collect. Do not post partial confirmations while the build is still moving.

## Concurrency evidence — what changed

`StockDocumentConcurrencyGuardTest` reads source files and asserts that the string
`lockForUpdate()` is present. That is an **architecture guard**. It proves a construct
was not deleted; it proves nothing about runtime behaviour, and the class docblock now
says so explicitly.

Executed proof lives in `scripts/wwhn219-runtime-concurrency.php`. For each scenario it:

1. builds an isolated fixture (never depending on business seed order),
2. spawns real OS processes via `proc_open`, one PostgreSQL backend each,
3. releases them together through a filesystem barrier,
4. has the lock winner hold the row for `WWHN219_LOCK_HOLD_MS` (default 1500ms),
5. samples `pg_stat_activity` / `pg_locks` from an independent monitor connection,
6. asserts the committed **ledger, balance and audit** state — not the HTTP status.

A scenario passes only when all of these hold: two distinct `pg_backend_pid()` values,
observed real contention, the expected number of successes, and the persisted invariants.

### Scenarios

| Scenario | Race | Invariant proven |
|---|---|---|
| `concurrent_post_receipt` | Two backends Post Receipt the same document | Exactly one stock effect; one movement; one `POST_RECEIPT` audit row; loser rejected with `409 STATE_CONFLICT` |
| `concurrent_reversal` | Two backends reverse the same posted receipt | Exactly one POSTED reversal; no over-reversal; balance never negative (BR-REV-09) |
| `shared_balance_lost_update` | Two different receipts hit one `inventory_balances` row | Both commit, effects are additive, `version` advances twice — no lost update |

Non-negative stock on the outbound path stays with
`Wwhn201PostIssueAtomicNonNegativeStockTest`: the database guard makes outbound
PRODUCT-only and requires matched items with active RFID, which is a fixture concern
separate from the lock semantics proven above.

## Permission catalog — why "31" was wrong

`DatabaseSeeder` → `AuthDatabaseSeeder` → `WmsPermissionCompatibilitySeeder`, and that
last seeder keeps upserting FE alias permissions. Any hand-counted constant or committed
snapshot drifts by construction. The catalog is therefore generated by querying
`permission` after seeding, and the manifest pins its SHA256.

The gate fails closed if the count is exactly 31, if `inventory.reversal.post` is not
ACTIVE, if a canonical reversal route loses its permission guard, or if any route URI
contains `apply-adjustment` or `stocktake`.

## RBAC assignment window (P0, fixed)

Running the suite for the first time exposed a live security hole: canonical
`user_roles` had no `effective_from` / `effective_to` columns, the `user_role`
compatibility view fabricated them as NULL, and `User::activeRoles()` treats NULL as
"always effective". Every expired or not-yet-valid role assignment therefore granted
permissions permanently, and `effective_to` could not revoke anything.

Disposition **Option A**, accepted 2026-08-16: keep the feature, restore the columns,
amend the ERD. Implemented in
`Modules/Warehouse/database/migrations/2026_08_16_000100_restore_user_role_effective_window.php`
with the matching Data Dictionary rows in `docs/HoaNam_ERD_Moi_Nhat.md` §4.

The trigger persists the window on both the INSERT and the `ON CONFLICT` branch —
omitting the conflict branch would have re-dropped it on every re-attach. Full detail
and the before/after measurements are in `SUITE-TRIAGE.md` §A1.

## apply-adjustment

Disposition **DISP-ADJ-001** (`docs/decision-records/DISPOSITION-APPLY-ADJUSTMENT.md`)
selects **Option B**: it is a business action name mapping to the append-only
Reversal/Correction endpoints, with no independent endpoint. Option A was rejected
because REQ-SRS-013 / BR-REV-01 forbid direct stock edit, the current-baseline contract
lists `stocktake` under `forbidden_path_fragments`, and
`Wwhn180PermissionAliasContractTest` asserts the route must not resolve.

Locked by `tests/Feature/Wwhn219ApplyAdjustmentDispositionTest.php`. Still requires a BA
Jira comment to move from `PENDING_BA_ACCEPT` to `ACCEPTED`.

## Closing order

Machine gates are decided by the build. Human gates are reported as `PENDING` and are
never auto-satisfied.

1. BA accepts DISP-ADJ-001 — **before** any further BE work depends on it.
2. BE changes land on `m1` only. Freeze.
3. Take the FINAL_SHA. Run the gate on that SHA.
4. QA1 retests that exact SHA and that exact artifact, then posts one consolidated comment.
5. Each role posts one consolidated comment. Tech Lead reviews last.
6. Request PM/reviewer re-evaluation of WWHN-219.

Supply the sign-off URLs to the manifest generator via `WWHN219_BA_SIGNOFF_URL`,
`WWHN219_QA1_SIGNOFF_URL` and `WWHN219_TECH_SIGNOFF_URL` so `acceptance_ready` can
become `true`.

## Reproducing locally

```bash
createdb wwhn219_verify
export DB_CONNECTION=pgsql DB_DATABASE=wwhn219_verify DB_USERNAME=postgres DB_PASSWORD=postgres
php artisan migrate:fresh --seed --force
php scripts/wwhn219-runtime-concurrency.php storage/app/wwhn-219-verify
php scripts/wwhn219-permission-catalog.php storage/app/wwhn-219-verify
php scripts/wwhn219-evidence-manifest.php storage/app/wwhn-219-verify
```

A local manifest will report `machine_gate_status: FAIL` because `FINAL_SHA` and the CI
run id are absent. That is intended — only CI can mint acceptance evidence.
